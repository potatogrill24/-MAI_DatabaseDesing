# Лабораторная работа 1

## Формулировка задания

1. Установить PostgreSQL и тестовые данные.
2. Выбрать модели самолетов, максимальная дальность полета которых находится в пределах от 4000 до 6000 км включительно.
3. Подсчитать количество мест для всех моделей самолетов с учетом класса обслуживания: бизнес и эконом. Группировать по `aircraft_code` и `fare_conditions`.
4. Найти количество красных и синих деталей.
5. Увеличить количество всех деталей, поставляемых для проекта 1, в два раза.
6. Найти проекты, для которых не поставляют красные детали, используя внешнее соединение.
7. Определить число маршрутов, обслуживаемых самолетами каждого типа. Сравнить внешнее и внутреннее соединение.
8. Определить, сколько деталей каждого цвета поставляют поставщики. Сравнить внешнее и внутреннее соединение на данном тестовом наборе.
9. Определить число пассажиров, не прошедших регистрацию.
10. Построить отчет по числу деталей весом в интервалах `[12,14)`, `[14,16)`, `[16,18)`, `[18,20)`. Для авиаперевозок построить аналогичный отчет по дальности в пределах `(0,100000)` км.

**Дополнительное задание.** Создать документную модель JSON: название проекта, необязательный приоритет, статус, массив задач с полями `id`, `title`, `date`. Вывести завершенные проекты, найти суммарную длительность проектов и суммарную длительность задач с наивысшим приоритетом.

## Файлы и запуск

Нужны две базы: `demo` из дампа и `simple` с таблицами `details`. Файлы их создания и инструкции установки тестовых данных находятся в [database_create](../database_create/README.md). Если базы уже созданы, пересоздавать их не требуется.

Команды выполняются из `MAI_DatabaseDesing` через `psql`:

```bash
# Пункт 1: проверка сервера и загруженных данных.
sudo -u postgres psql -X -d postgres -f lab_01/00_check_setup.sql

# Пункты 2, 3, 7, 9, 10: авиаперевозки.
sudo -u postgres psql -X -d demo -f lab_01/01_airlines.sql

# Пункты 4, 6, 8, 10: детали и поставки, до изменения количества.
sudo -u postgres psql -X -d simple -f lab_01/02_details.sql

# Пункт 5: удвоение поставок проекта 1 с сохранением изменений.
sudo -u postgres psql -X -d simple -f lab_01/03_double_project_1.sql

# Дополнительное задание: JSON-документы в базе simple.
sudo -u postgres psql -X -d simple -f lab_01/04_projects_json.sql
```

Все файлы включают `ON_ERROR_STOP`: при ошибке выполнение прекращается. Для проверки кода завершения выполните `echo $?` сразу после запуска; ожидается `0`. Пункт 5 вынесен отдельно: **каждый запуск снова удваивает количества**. Для возвращения исходных данных можно пересоздать `simple` скриптом из `database_create`, при этом удалятся все ее изменения и JSON-документы.

## Пояснения и проверка

- В данном дампе `aircraft_code` называется `airplane_code`, а перелеты билетов хранятся в `segments` вместо `ticket_flights`. Код использует фактическую структуру. Названия самолетов выводятся по-русски.
- Пункт 2 возвращает **E70 (4000 км)** и **76F (6000 км)**: обе границы включены.
- Пункт 3 показывает Business и Economy для каждой модели, в том числе нулевые количества. Доступный в дампе Comfort в этот отчет не включен.
- Пункт 4 считает наименования в справочнике: **2 красных и 2 синих**. Пункт 8 считает поставленные единицы через `SUM(qty)`, а не число строк поставок. Повторяющаяся поставка из исходных данных учитывается дважды.
- Пункт 5 на исходных данных меняет 4 строки: суммарное количество для `j1` увеличивается с **1000 до 2000**.
- Пункт 6 на исходных данных дает **пустой результат**: всем семи проектам поставляются красные детали. Проверяется отсутствие любых красных поставок, а не наличие поставок другого цвета.
- В пункте 7 считается `COUNT(DISTINCT route_no)` по всем версиям расписания. `LEFT JOIN` возвращает 10 типов, `INNER JOIN` — 8: грузовые `35X` и `76F` имеют ноль маршрутов.
- В пункте 8 оба соединения дают одинаковые **9 строк**: все поставщики имеют поставки, ссылки на детали корректны. Если добавить поставщика без поставок, только внешний вариант сохранит его с нулевым количеством.
- В пункте 9 пассажир учитывается один раз, если у него есть хотя бы один перелет без посадочного талона. Соединение выполняется по билету **и рейсу**. Основной запрос включает будущие рейсы и дает **773080 пассажиров**; дополнительный рассматривает только уже вылетевшие относительно `bookings.now()` и дает **0**.
- Весовые интервалы в пункте 10 дают **2, 1, 2, 1** наименования. Левая граница включена, правая исключена. Для дальности шаг в задании не указан, поэтому выбран **10000 км**: в первых двух интервалах 6 и 4 модели, далее нули. Общий подсчет в открытом диапазоне `(0,100000)` — **10 моделей**. Считаются модели из справочника, не отдельные физические борта.

## Документная модель

Документы хранятся в `documents.projects.document` типа `jsonb`. Приоритеты: `low`, `normal`, `high`; отсутствие поля означает `normal`. Статусы: `planned`, `active`, `completed`. Задачи наследуют приоритет проекта.

Одной даты `date` недостаточно для вычисления длительности, поэтому задачи дополнены полем `duration_days`. В этой модели длительность проекта — сумма длительностей задач, то есть трудозатраты, а не календарный промежуток между первой и последней датой. Это явное допущение для недоопределенной части условия.

На исходных документах завершены проекты **1 и 3**, общая длительность равна **9 дням**, длительность задач высокого приоритета — **5 дням**. Проект с пустым массивом задач сохраняется в отчете с длительностью 0. Повторный запуск не дублирует документы и не перезаписывает существующие записи с теми же идентификаторами.

Все пять SQL-файлов проверены на отдельной копии исходного дампа и базы `simple` в PostgreSQL 18. Рабочие базы при этой проверке не изменялись.
