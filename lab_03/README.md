# Лабораторная работа 3

## Формулировка задания

Отработать транзакции на базе «Авиаперевозки» с уровнем изоляции **Read Committed**:

1. Создать бронирование `ABC123` с датой `bookings.now()` и первоначальной суммой `total_amount = 0`.
2. Оформить два билета: `9991234567890` для `IVAN PETROV`, паспорт `1234 123456`, и `9991234567891` для `PETR IVANOV`, паспорт `4321 654321`.
3. Каждому пассажиру добавить два перелета Москва — Красноярск и обратно: Business за 12500 и Economy за 8500. В исходном примере указаны рейсы 5572 и 13881.
4. Подсчитать сумму всех забронированных перелетов и записать ее в `bookings.total_amount`.
5. Реализовать автоматический подсчет `total_amount` с помощью триггера.

## Файлы и запуск

Используется восстановленная база `demo`. Команды выполняются из `MAI_DatabaseDesing`:

```bash
# Функция и триггер для суммы бронирования.
sudo -u postgres psql -X -d demo -f lab_03/00_total_amount_trigger.sql

# Создание и сохранение бронирования по заданию.
sudo -u postgres psql -X -d demo -f lab_03/01_create_booking.sql

# Проверка INSERT, UPDATE, DELETE, переноса сегмента и SAVEPOINT.
sudo -u postgres psql -X -d demo -f lab_03/02_check.sql
```

Все скрипты включают `ON_ERROR_STOP`: при ошибке выполнение прекращается. Для проверки кода завершения сразу после запуска выполните `echo $?`; ожидается `0`.

`01_create_booking.sql` заканчивается **COMMIT** и сохраняет данные. Повторный запуск с теми же номерами завершится ошибкой: существующие записи не удаляются и не перезаписываются. Для нового примера нужны другие номера бронирования и билетов. Для пробного запуска можно заменить финальный `COMMIT` на `ROLLBACK`.

`02_check.sql` использует отдельные тестовые бронирования `F0A003`, `F0A004` и билеты `9990000000001`–`9990000000003`; эти идентификаторы должны быть свободны. Все его данные отменяются финальным `ROLLBACK`, поэтому проверку можно повторять. Бронирование `ABC123` не меняется.

## Адаптация к дампу

В дампе версии 2025 таблица `ticket_flights` называется `segments`, стоимость `amount` — `price`. В `tickets` обязательно поле `outbound`; оно заполнено значением `TRUE`.

Старые номера рейсов не гарантируют тот же маршрут в новом наборе. Скрипт находит реальные рейсы по городам и представлению `timetable`, которое учитывает период действия маршрута. Прямой вылет выбирается не раньше `bookings.now()`, обратный — после прибытия в Красноярск; отмененные рейсы исключены. Найденные номера и даты выводятся перед вставкой данных.

На исходном дампе выбраны рейсы **11515 и 12138** с вылетами 3 и 7 декабря 2025 года. Дата бронирования из `bookings.now()` — 1 декабря 2025 года; это условная дата набора данных, а не системная дата запуска.

По условию сохраняются именно два билета с двумя сегментами каждый. Это адаптация старого примера: поле `outbound` новой модели задается на уровне билета, а отдельного признака направления для каждого сегмента здесь нет. Проверка свободных мест и тарифных правил в задачу не входит.

## Транзакция и триггер

`BEGIN ISOLATION LEVEL READ COMMITTED` объединяет бронирование, билеты и перелеты в одну транзакцию. Ошибка до `COMMIT` отменяет весь пример при завершении подключения. На уровне Read Committed каждый оператор получает снимок уже зафиксированных данных к началу этого оператора; собственные изменения транзакции также видны.

Триггер `lab03_segments_total` срабатывает **AFTER INSERT OR UPDATE OR DELETE** для каждой строки `segments`:

- INSERT прибавляет новую цену.
- DELETE вычитает старую цену.
- UPDATE вычитает старую цену и прибавляет новую; при смене билета учитывает соответствующие бронирования.

Изменение выполняется через `total_amount = total_amount + delta`. Конкурентные изменения одной строки бронирования сериализуются блокировкой строки, что предотвращает потерю прибавлений. Пересчет через обычный `SUM` в триггере без дополнительной синхронизации мог бы не увидеть незафиксированные сегменты другой транзакции.

Триггер не пересчитывает старые суммы при установке и предполагает, что они изначально корректны, а новые бронирования создаются с нулевой суммой. Ручное изменение `total_amount`, перенос целого билета через `tickets.book_ref`, `TRUNCATE` и загрузка с отключенными триггерами выходят за рамки этого решения. В сложных конкурирующих транзакциях возможны взаимоблокировки; такие транзакции повторяют после отката.

## Проверка результата

При создании бронирования выводятся суммы **0 → 21000 → 42000**. Итоговая выборка показывает **2 билета, 4 сегмента**, хранимую и независимо вычисленную суммы **42000**. Скрипт проверяет итог и выдает ошибку, если триггер не сработал.

`02_check.sql` проверяет суммы 300 после INSERT, 350 после изменения цены, 150 после DELETE, перенос 150 между бронированиями и восстановление 300/0 после `ROLLBACK TO SAVEPOINT`. При успехе выводится **«Все проверки пройдены»**, затем тестовые данные откатываются.

Без триггера итог можно было бы записать явно, как предлагается в первой части задания:

```sql
UPDATE bookings.bookings b
SET total_amount = (
	SELECT coalesce(sum(s.price), 0)
	FROM bookings.tickets t
	JOIN bookings.segments s
		ON s.ticket_no = t.ticket_no
	WHERE t.book_ref = b.book_ref
)
WHERE b.book_ref = 'ABC123';
```

В основном решении этот UPDATE не нужен: сумму поддерживает триггер. Для просмотра сохраненного результата:

```sql
SELECT *
FROM bookings.bookings
WHERE book_ref = 'ABC123';

SELECT t.ticket_no, t.passenger_name, s.flight_id, s.fare_conditions, s.price
FROM bookings.tickets t
JOIN bookings.segments s
	ON s.ticket_no = t.ticket_no
WHERE t.book_ref = 'ABC123'
ORDER BY t.ticket_no, s.flight_id;
```

Все три скрипта проверены на отдельной копии исходного дампа в PostgreSQL 18. Дополнительно проверены отказ повторного создания `ABC123`, откат всего бронирования при ошибке после вставки сегмента и конкурентные вставки цен 100 и 200: итог равен 300, прибавления не теряются. Рабочая база при проверке не изменялась.
