# Лабораторная работа 4

## Формулировка задания

1. Создать индекс по `passenger_name` и `passenger_id` таблицы `tickets`. Проверить, потребовался ли временный файл при построении индекса. Посмотреть план запроса всех мест в салонах в порядке кодов самолетов, оформленного как курсор. Уменьшить `cursor_tuple_fraction` в десять раз и объяснить изменение плана.
2. Написать запрос занятых мест для всех рейсов. Определить выбранный способ соединения и достаточность памяти для хеш-таблиц. Изменить запрос так, чтобы он возвращал только общее число занятых мест. Сравнить планы и объяснить, почему аналогичный план не выбран для подробной выборки.
3. Написать запрос максимальной суммы бронирования. Определить метод доступа и оценить его эффективность. Создать индекс по `bookings.total_amount`, повторить проверку плана и объяснить результат.

## Файлы и запуск

Используется восстановленная база `demo`. Команды выполняются из `MAI_DatabaseDesing`:

```bash
# Настройки, статистика и исходные индексы.
sudo -u postgres psql -X -d demo -f lab_04/00_prepare.sql

# Пункт 1: составной индекс, временные файлы и курсор.
sudo -u postgres psql -X -d demo -f lab_04/01_index_and_cursor.sql

# Пункт 2: подробная выборка мест и агрегат COUNT.
sudo -u postgres psql -X -d demo -f lab_04/02_occupied_seats.sql

# Пункт 3: MAX до и после индекса.
sudo -u postgres psql -X -d demo -f lab_04/03_max_booking.sql
```

Все файлы включают `ON_ERROR_STOP`. Сразу после запуска команда `echo $?` должна показать `0`. `00_prepare.sql` обновляет статистику через `ANALYZE`, чтобы оценки соответствовали данным.

Созданные индексы **сохраняются**: `lab04_tickets_name_id_idx` и `lab04_bookings_total_amount_idx`. Повторный запуск не удаляет и не перестраивает их благодаря `IF NOT EXISTS`. Поэтому временные файлы построения проверяют при первом создании, а повторный план «до» уже может использовать ранее созданный индекс. Список исходных индексов выводится в `00_prepare.sql`; чужие индексы скрипты не удаляют.

`EXPLAIN ANALYZE` действительно выполняет запрос, но выводит план вместо миллионов строк. Для подробной выборки отдельно показаны любые десять строк; этот `LIMIT` не участвует в сравнении основных планов. В данном дампе код самолета называется `airplane_code`.

## Пункт 1. Индекс и курсор

Создается один составной B-tree по `(passenger_name, passenger_id)`: сначала упорядочение по имени, затем по идентификатору. Для проверки временных файлов сессия включает `log_temp_files=0`, а `client_min_messages=log` позволяет увидеть сообщения `temporary file` в выводе. Изменения этих настроек локальны для транзакции построения индекса.

`CREATE INDEX` нельзя исследовать через `EXPLAIN`; ответ о временных файлах берется из сообщений журнала, а не из размера индекса или длительности команды. Для изменения `log_temp_files` нужны соответствующие права; при их отсутствии скрипт явно сообщает, что понадобится журнал администратора. Запуск от `postgres` дает необходимые права.

**На проверочной копии временные файлы потребовались:** при `maintenance_work_mem=64MB` зарегистрированы два файла размером **67592192 и 68354048 байт**. Они относятся к параллельному построению индекса. Само построение заняло около 16,580 с. Сообщения сохранены в [протоколе пункта 1](results/01_index_and_cursor.txt).

Исходный SQL демонстрации не приложен, поэтому используется запрос из ее текстового описания:

```sql
DECLARE seats_demo CURSOR FOR
	SELECT *
	FROM bookings.seats
	ORDER BY airplane_code;
```

Планы проверяются через `EXPLAIN DECLARE`, чтобы учитывался именно курсор. Затем `cursor_tuple_fraction` делится на 10 относительно текущего значения. Меньшее значение означает ожидание чтения меньшей части результата и повышает важность стоимости получения первых строк; оно не ограничивает фактическое число строк курсора. Настройка возвращается к исходной после `COMMIT`.

**Полученный результат:** при переходе **0,1 → 0,01 план не изменился** — в обоих случаях `Index Scan using seats_pkey`, оценка 1741 строк. Первичный ключ `(airplane_code, seat_no)` уже дает нужный порядок кодов самолетов без отдельной сортировки. Уменьшение доли не обязано приводить к другому плану: здесь этот доступ выгоден в обоих случаях.

## Пункт 2. Занятые места и COUNT

Занятым считается место, назначенное пассажиру в `boarding_passes`. Соединяются рейсы, посадочные талоны и билеты; выводятся рейс, дата, место, номер билета и имя пассажира. Отдельная строка для рейса без занятых мест не нужна: запрос перечисляет сами занятые места. Регистрация не равнозначна фактической посадке; фильтр по `boarding_time` не добавляется.

Основное сравнение выполняется для **одинаковых соединений**: сначала с подробными столбцами, затем с `COUNT(*)`. Для узлов `Hash` и `Parallel Hash` смотрят `Batches`, `Memory Usage` и `Buffers`:

- `Batches: 1` означает, что хеширование выполнено без разбиения на дисковые пакеты.
- `Batches > 1` указывает на использование временных данных; `temp read/written` показывает временные чтения и записи.
- `work_mem` не является общим лимитом памяти на весь запрос; для хеширования учитывается также `hash_mem_multiplier`.

**На проверочной копии** подробный запрос вернул по плану **2463832 строки** и использовал два `Hash Join`:

| Хеш-таблица | Batches | Memory Usage | Вывод |
|---|---:|---:|---|
| Билеты `tickets` | 32 | 6434 kB | Целиком в выделенную память не поместилась |
| Рейсы `flights` | 1 | 1446 kB | Поместилась в память |

Для подробного запроса также зафиксированы `temp read=29514 written=29514`. При `COUNT(*)` тех же соединений появились `Parallel Hash Join`, `Gather`, `Partial Aggregate` и `Finalize Aggregate`. Хеш билетов по-прежнему имеет **32 пакета**, поэтому одна итоговая строка не означает, что все промежуточные данные поместились в память. Полные планы находятся в [протоколе пункта 2](results/02_occupied_seats.txt).

Для агрегата параллельные работники могут передать через `Gather` несколько частичных счетчиков вместо миллионов полных строк. Поэтому параллельное выполнение и частичная агрегация могут оказаться выгодными для `COUNT`, даже когда подробная выборка получает последовательный план. Кроме того, агрегату не нужны широкие столбцы вроде имени пассажира. Это объяснение выбранного плана по модели стоимости, а не запрет параллельной подробной выборки.

Дополнительно показан `COUNT(*) FROM bookings.boarding_passes`: без фильтров по связанным таблицам соединения можно убрать, поскольку внешние ключи гарантируют существование связанных билета и рейса. Этот вариант вынесен отдельно и не подменяет сравнение одинаковых соединений.

## Пункт 3. Максимальная сумма

Основной запрос:

```sql
SELECT max(total_amount)
FROM bookings.bookings;
```

Без подходящего индекса максимум приходится искать чтением всех сумм: обычно выбираются последовательное чтение и агрегат, иногда параллельные. При отсутствии упорядоченного доступа такой способ обоснован, но объем работы растет с таблицей.

После создания B-tree по `total_amount` планировщик может использовать `Limit` и обратное чтение индекса, взяв одну крайнюю подходящую запись. При `Index Only Scan` нужно также смотреть `Heap Fetches`: проверка видимости иногда требует обращения к самой таблице. Стоимость создания индекса не входит во время последующего SELECT; индекс также требует места и обслуживания при изменении данных.

**На проверочной копии** до индекса получен `Parallel Seq Scan` с частичной и финальной агрегацией; после — `InitPlan → Limit → Index Only Scan Backward`. После индекса прочитана одна индексная запись, `Heap Fetches: 0`. Максимальная сумма — **915250,00**. Подробности — в [протоколе пункта 3](results/03_max_booking.txt).

## Как читать результаты

Сравнивайте узлы плана, `rows` и `actual rows`, временные блоки и `Execution Time`. В узлах с несколькими `loops` значение `actual rows` усреднено за выполнение узла; учитывайте число циклов. `cost` — условная оценка планировщика, а не миллисекунды.

Планы зависят от версии PostgreSQL, статистики, памяти, настроек параллелизма и уже существующих индексов. Время также зависит от нагрузки и кеша; одинаковые времена при повторении не требуются.
