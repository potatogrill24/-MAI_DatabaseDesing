# Лабораторная работа 5

## Формулировка задания

Создать индекс на таблице билетов `tickets` по имени пассажира `passenger_name`. Определить, какая статистика имеется для таблицы. Объяснить оценку кардинальности и выбор плана следующих запросов:

а) выборка всех билетов;

б) выборка билетов на имя `ALEKSANDR IVANOV`;

в) выборка билетов на имя `ANNA VASILEVA`;

г) выборка билета с идентификатором `0005432000284`.

## Файлы и запуск

Используется восстановленная база `demo`. Команды выполняются из `MAI_DatabaseDesing`:

```bash
# Индекс имени, сбор и просмотр статистики.
sudo -u postgres psql -X -d demo -f lab_05/00_index_and_statistics.sql

# Четыре запроса, планы и фактические количества строк.
sudo -u postgres psql -X -d demo -f lab_05/01_query_plans.sql

# Расчет оценки равенства по MCV и числу различных имен.
sudo -u postgres psql -X -d demo -f lab_05/02_cardinality.sql
```

Все файлы включают `ON_ERROR_STOP`. Сразу после запуска команда `echo $?` должна показать `0`. Скрипты не меняют билеты; индекс `lab05_tickets_passenger_name_idx` **сохраняется**, а `ANALYZE` обновляет статистику. Повторное создание индекса пропускается через `IF NOT EXISTS`.

В лабораторной 4 создавался составной индекс `(passenger_name, passenger_id)`. Он тоже подходит для поиска по имени, поскольку имя — его первый столбец. Поэтому планировщик вправе выбрать его вместо нового индекса; имеющиеся индексы выводятся перед планами. Скрипты ничего не удаляют и не запрещают планировщику выбирать доступные способы доступа.

`EXPLAIN ANALYZE` выполняет запрос целиком, но печатает план вместо всех возвращаемых строк. Поэтому пункт а) не выводит миллионы билетов в терминал. Для сверки в конце скрипта отдельно подсчитываются результаты всех четырех запросов и выводится билет из пункта г).

## Какая статистика используется

| Источник/поле | Значение для планировщика |
|---|---|
| `pg_class.reltuples` | Оценка количества строк таблицы |
| `pg_class.relpages` | Число страниц таблицы по последнему обновлению статистики |
| `pg_stats.null_frac` | Доля NULL в столбце |
| `avg_width` | Средняя ширина значения в байтах |
| `n_distinct` | Оценка числа различных значений; отрицательное число задает долю от количества строк |
| `most_common_vals` | Список наиболее частых значений, MCV |
| `most_common_freqs` | Частота каждого значения из MCV как доля всех строк |
| `histogram_bounds` | Границы гистограммы значений вне MCV, используемые прежде всего для диапазонов |
| `correlation` | Корреляция логического порядка значений с физическим расположением строк; влияет на стоимость индексного доступа |
| `pg_stats_ext` | Расширенные статистики по группам столбцов и выражениям, если они созданы |

Например, `n_distinct=-1` означает, что все значения различны; `-0.5` — примерно одно различное значение на две строки таблицы. Для отрицательной величины число различных значений оценивается как `-n_distinct × N`.

Обычный `CREATE INDEX` не заменяет `ANALYZE`: статистика столбцов собирается отдельно по выборке. После повторного анализа оценки и MCV могут немного измениться. Кроме статистики, планировщик учитывает уникальные ограничения и стоимость чтения страниц.

## Оценка кардинальности

Кардинальность — ожидаемое количество строк результата. Для фильтра равенства:

```text
ожидаемые строки ≈ N × селективность
```

Если имя входит в MCV, селективность берется из соответствующей частоты. Если его там нет, оставшаяся вероятность распределяется по остальным различным значениям:

```text
селективность ≈ (1 − null_frac − сумма частот MCV)
                / (число различных значений − количество MCV)
```

Расчет в `02_cardinality.sql` показывает исходные величины, наличие имени в MCV и итоговую оценку. Дополнительно учитывается верхняя граница по частоте наименее частого MCV. Это иллюстрация оценки равенства на данном наборе, а не реализация всего планировщика.

Для равенства используется прежде всего MCV и число различных значений; наличие гистограммы не означает, что она дает точную частоту произвольного имени. Отсутствие имени в MCV также не доказывает отсутствие имени в таблице.

В сохраненном запуске для `passenger_name` получены `null_frac=0`, `n_distinct=149303`, **76 значений MCV** с суммарной частотой **0,020033324**. Оба имени из задания не входят в MCV. При оценке таблицы `N=2973949` расчет дает примерно **19,53**, после округления — **20 строк** для каждого имени. Полный расчет сохранен в [протоколе оценки кардинальности](results/02_cardinality.txt).

## Объяснение четырех планов

**а) Все билеты.** Селективность равна 1: нужно вернуть всю таблицу со всеми столбцами. Последовательное чтение обычно дешевле обхода индекса имени с последующим получением каждой полной строки из таблицы. Оценка строк берется из размера таблицы и `reltuples`; это не обязательно точный `COUNT(*)`.

**б), в) Поиск по имени.** Планировщик оценивает количество подходящих билетов по частотам и `n_distinct`. При небольшой оценке выгоден индекс имени. Вариант `Bitmap Index Scan → Bitmap Heap Scan` сначала собирает адреса строк, затем читает страницы таблицы; группировка обращений по страницам снижает стоимость поиска нескольких строк. При другой оценке и настройках может быть выбран обычный `Index Scan` или последовательное чтение. Индекс только имени не содержит всех столбцов `SELECT *`, поэтому для найденных строк нужен доступ к таблице.

**г) Точный номер билета.** `ticket_no` — первичный ключ, поэтому подходящих строк не больше одной. Используется уже существующий индекс `tickets_pkey`, а не индекс имени. Номер задан строкой: ведущие нули являются частью идентификатора.

## Проверка результатов

Сопоставляйте `rows` и `actual rows` соответствующего узла. Для узлов с несколькими `loops` фактическое число строк усредняется за выполнение узла. `cost` измеряется в условных единицах, время исполнения — в `Execution Time`, чтение страниц — в `BUFFERS`.

Планы и результаты проверки на отдельной копии дампа сохраняются в `results`. Конкретные оценки зависят от выборки `ANALYZE`, версии сервера, данных, настроек и имеющихся индексов; совпадение времен исполнения не требуется.

Проверка выполнена в **PostgreSQL 18.6** на исходном дампе версии 2025, с `default_statistics_target=100`, `random_page_cost=4`, `seq_page_cost=1`, `work_mem=4MB`. Рабочая база не изменялась. В таблице **2973937 билетов**, 30744 страницы, размер основной таблицы — 240 MB. Оценка `reltuples` после анализа — 2973949, то есть на 12 больше фактического количества.

| Запрос | Оценка строк | Фактически | Выбранный план в основном запуске |
|---|---:|---:|---|
| а) Все билеты | 2973949 | 2973937 | Seq Scan |
| б) ALEKSANDR IVANOV | 20 | 0 | Bitmap Index Scan по индексу имени → Bitmap Heap Scan |
| в) ANNA VASILEVA | 20 | 0 | Bitmap Index Scan по индексу имени → Bitmap Heap Scan |
| г) Номер 0005432000284 | 1 | 1 | Index Scan по tickets_pkey |

**Отсутствие обоих имен — свойство данного дампа.** Запросы используют точное написание из задания и не заменяют его другими именами. Планировщик оценивает неизвестное ему имя через статистическую модель, поэтому положительная оценка при нулевом фактическом результате объяснима. Частотного различия между двумя заданными именами на этом наборе не получается.

Во всех пяти столбцах `null_frac=0`. У `ticket_no` значение `n_distinct=-1`, а корреляция с физическим порядком около 0,99986; у имени корреляция около 0,00159, то есть почти отсутствует. Расширенных статистик для `tickets` в исходном дампе нет. Полные списки MCV, частоты, гистограммы и сведения об индексах находятся в [протоколе статистики](results/00_index_and_statistics.txt), планы четырех запросов — в [основном протоколе](results/01_query_plans.txt).
