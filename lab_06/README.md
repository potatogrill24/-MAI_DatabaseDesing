# Лабораторная работа 6

## Формулировка задания

Оптимизировать запрос контактной информации пассажиров, летевших бизнес-классом, рейсы которых были задержаны более чем на 5 часов. Начать с варианта:

```sql
SELECT t.*
FROM tickets t, ticket_flights tf, flights f
WHERE tf.ticket_no = t.ticket_no
	AND f.flight_id = tf.flight_id
	AND tf.fare_conditions = 'Business'
	AND f.actual_departure > f.scheduled_departure + interval '5 hour';
```

## Файлы и запуск

Используется восстановленная база `demo`. В текущем дампе `ticket_flights` называется **segments**. Команды выполняются из `MAI_DatabaseDesing`:

```bash
# Исходный запрос, настройки, селективность условий и план.
sudo -u postgres psql -X -d demo -f lab_06/00_original.sql

# Дополнительно: непустой проверочный набор, планы и граничные случаи.
# Для сравнения до создания новых индексов удобнее выполнить его сейчас.
sudo -u postgres psql -X -d demo -f lab_06/04_check_nonempty.sql

# Постоянное создание индексов и сбор статистики.
sudo -u postgres psql -X -d demo -f lab_06/01_indexes.sql

# Оптимизированный план и результат запроса.
sudo -u postgres psql -X -d demo -f lab_06/02_optimized.sql

# Проверка равенства исходного и оптимизированного результатов.
sudo -u postgres psql -X -d demo -f lab_06/03_check.sql
```

Все файлы включают `ON_ERROR_STOP`. Сразу после команды запуска `echo $?` должен показать `0`. Созданные через `01_indexes.sql` индексы **сохраняются**, повторное создание пропускается через `IF NOT EXISTS`. Старые индексы не удаляются; уже имеющиеся индексы влияют на исходный план при повторении эксперимента.

`04_check_nonempty.sql` добавляет пять искусственных рейсов, пять билетов и шесть сегментов только внутри одной транзакции. После сравнения он выполняет `ROLLBACK`: тестовые данные и созданные внутри него индексы отменяются, ранее существовавшие индексы остаются. Если запустить сценарий после `01_indexes.sql`, исходный запрос тоже сможет использовать уже существующие индексы. Сценарий не меняет время вылета реальных рейсов.

Тест использует бронирование `LAB006`, билеты `9996000000001`–`9996000000005` и рейсы с ID от `-600005` до `-600001`. Эти идентификаторы должны быть свободны; при конфликте выполнение останавливается, чужие записи не перезаписываются.

## Ограничение контактных данных

В данном дампе у `tickets` есть только `ticket_no`, `book_ref`, `passenger_id`, `passenger_name`, `outbound`. **Телефонов, email и поля contact_data нет.** Поэтому `t.*` возвращает имеющиеся данные билета, а получить реальные контакты из этого дампа невозможно. Новые контактные данные в решении не выдумываются.

Ниже оптимизируется именно предложенная выборка с сохранением всех ее строк. Для получения контактов нужен их источник или версия базы, где они уже присутствуют. В старой схеме с `tickets.contact_data` и `ticket_flights` в итоговом запросе заменяется название `segments`; `t.*` тогда включает и контакты. Планы и времена, приведенные здесь, относятся к фактическому текущему дампу.

## Оптимизация

Итоговый запрос:

```sql
SELECT t.*
FROM bookings.flights f
JOIN bookings.segments s
	ON s.flight_id = f.flight_id
	AND s.fare_conditions = 'Business'
JOIN bookings.tickets t
	ON t.ticket_no = s.ticket_no
WHERE f.actual_departure - f.scheduled_departure > interval '5 hour';
```

Явные JOIN делают связи читаемее, но сами по себе обычно не ускоряют исходный запрос. Порядок таблиц в тексте также не закрепляет порядок соединений. Существенные изменения — индексируемое выражение задержки, подходящий индекс бизнес-сегментов и статистика.

Для интервала ровно из пяти часов условие переписано в эквивалентную разность временных отметок. NULL по-прежнему не проходит фильтр; задержка ровно на 5 часов исключается. Такое преобразование нельзя автоматически переносить на календарные интервалы вроде `1 day`, которые в часовых поясах с переходом времени могут отличаться от 24 часов.

Созданы индексы:

```sql
CREATE INDEX lab06_flight_delay_idx
	ON bookings.flights ((actual_departure - scheduled_departure))
	INCLUDE (flight_id);

CREATE INDEX lab06_business_segments_idx
	ON bookings.segments (flight_id, ticket_no)
	WHERE fare_conditions = 'Business';
```

Первый индекс позволяет искать задержки по диапазону. После `ANALYZE` для выражения появляется статистика: планировщик лучше оценивает редкие задержанные рейсы. `flight_id` хранится как полезная нагрузка для соединения; конкретный план может использовать обычный Index Scan или bitmap-доступ.

Второй индекс содержит только Business и начинается с `flight_id`: по найденному рейсу можно получить номера бизнес-билетов без чтения всех сегментов. Полные строки билетов затем извлекаются по существующему первичному ключу `tickets_pkey`.

Функция вычитания двух `timestamptz` имеет категорию **IMMUTABLE**, а сложение `timestamptz + interval` — **STABLE** из-за календарной арифметики. Поэтому исходное сложение нельзя просто перенести в индексное выражение или предикат индекса: требуется IMMUTABLE. `01_indexes.sql` показывает категории используемых функций и статистику выражения; принудительное изменение категорий не применяется.

Индексы занимают место и обслуживаются при изменениях. Их построение и `ANALYZE` не включаются во время последующей выборки. Для одного запуска на небольшом или пустом результате расходы создания индексов могут быть больше экономии на запросе.

## Проверка корректности

`03_check.sql` сравнивает результаты в обе стороны через **EXCEPT ALL**. Ожидается сообщение **«Проверка пройдена: различий 0, повторения совпадают»**. Учитываются не только значения строк, но и число их повторений. Проверка сравнивает оба запроса в рамках одного SQL-снимка.

Один билет может иметь несколько задержанных бизнес-перелетов и появляться несколько раз. Замена JOIN на EXISTS убрала бы эти повторения, поэтому такой вариант не используется как полностью эквивалентная оптимизация. Одна строка на пассажира — отдельное требование, которого исходный запрос не обеспечивает.

Для добавленных тестовых билетов ожидается **3 строки для 2 билетов**: два подходящих перелета одного билета и один перелет другого. Economy на задержанном рейсе, Business с задержкой ровно 5 часов и Business без фактического вылета должны быть исключены. Задержка 5 часов 1 секунда должна попасть в результат. При успехе выводится сообщение о прохождении граничных случаев.

## Результаты проверки

Полные протоколы отдельной проверки сохраняются в `results`. Сравниваются `Execution Time`, выбранные узлы, оценка `rows`, фактическое `actual rows` и `BUFFERS`; одинаковое время при повторении не требуется. Состояние кеша, статистическая выборка, версия сервера и существующие индексы влияют на результаты.

Проверка выполнена на отдельной копии исходного дампа в **PostgreSQL 18.6**, с `work_mem=4MB`, `random_page_cost=4` и максимум двумя дополнительными работниками на параллельный запрос. Рабочая база не изменялась.

В исходных данных **21758 рейсов, 3941249 сегментов, из них 417644 — Business**. **Рейсов с задержкой более пяти часов нет**, поэтому результат обоих запросов пустой. Это подтверждено [исходным протоколом](results/00_original.txt). Непустой сценарий нужен именно для проверки реальной выдачи, границы условия и повторений.

| Набор данных | Строк результата | Исходный запрос | Оптимизированный запрос |
|---|---:|---:|---:|
| Исходный дамп | 0 | 24,854 мс | 0,040 мс |
| Дамп с временным проверочным набором | 3, из них 2 строки одного билета | 164,066 мс | 0,043 мс |

Это значения `Execution Time` отдельных запусков `EXPLAIN ANALYZE`, без времени построения индексов и планирования. На исходном наборе создание двух индексов заняло около **0,273 и 2,191 с**, а последующий `ANALYZE` — около **0,695 с**: для единственного пустого запроса создавать их ради такого измерения дороже, чем выполнить исходную выборку.

Исходный план использовал `Parallel Hash Join` и последовательное чтение. Для фильтра задержки планировщик оценивал **7253 рейса вместо 0**: сложное сравнение без подходящей статистики получило стандартную селективность порядка 1/3. После индекса выражения оценка уменьшилась до **1**, а план стал `Nested Loop`: индекс задержки → индекс бизнес-сегментов → `tickets_pkey`. На пустом наборе последние два доступа не выполнялись, поскольку первый не нашел рейсов.

В непустом сценарии оценка рейсов улучшилась с **7254 до 65**, фактически их **3**. Она осталась неточной, но уже привела к выгодному плану: `Bitmap Index Scan`/`Bitmap Heap Scan` по задержке, `Index Only Scan` бизнес-сегментов и `Index Scan` по первичному ключу билетов. В этом Index Only Scan были `Heap Fetches: 3`: название узла не гарантирует отсутствия обращений к таблице для проверки видимости.
